# Iteration 4 — Is `skip_initramfs` gated on AVB / boot-image shape?

Analysis only. No device writes, no flashing, no reboot.
New reads this iteration: `by-name/abl` (sdd6, 4 MiB), `artifacts/known-good/stock-boot.img`.

---

## 1. What ABL is most likely doing, and why

Samsung ABL is applying the **Android 10+ "system-as-root" boot contract**, in
which the boot image carries **no ramdisk** and the kernel is told to mount the
system partition directly:

```
/chosen/bootargs  =  <~2.4 KB generated by ABL>  +  <133 bytes AVB/dm-verity layer>
                                  ^
                    our BOARD_KERNEL_CMDLINE is only an INPUT here
```

Evidence for the size of ABL's own contribution:

* ABL's AVB ledger starts at `DstLen 4296`, so ~2.4 KB were already in the
  buffer before any logged append.
* The only complete ABL-generated cmdline we can read — the **recovery** one —
  is **2511 chars**, almost entirely `androidboot.*` properties ABL synthesises
  itself (`serialno`, `dtbo_idx`, `sec_atd.tty`, `sec_log=0x200000@0xC1600000`,
  `wb.*`, `em.*`, `carrierid`, …). None of it is in our header cmdline.
* `drivers/of/fdt.c:1190-1240` with `read_dt_cmdline=1, concat_cmdline=0`:
  `strlcpy(cmdline, p, ...)` — **`/chosen/bootargs` replaces
  `boot_command_line` wholesale.** We control nothing on the final command line.

`skip_initramfs` is the flag that tells the kernel "there is no initrd; do not
try". `root=PARTUUID=<system>` tells it where the root is. Both are the same
contract. ABL writes `/chosen/bootargs` itself (`last_kmsg:13832 Update Device
Tree total time: 140 ms`).

## 2. Evidence for / against AVB state causing `skip_initramfs`

### Against — three independent arguments, the first is close to decisive

**(a) The recovery boot has the *same* AVB state and does not have the token.**

| | our normal boot | recovery boot (cmdline fully readable) |
|---|---|---|
| `IsUnlocked` | `(1)` | `(1)` |
| `Boot State is` | `1` | `1` |
| `verifiedbootstate` | `orange` | `orange` |
| `ulcnt` | `2` | `2` |
| `GetUnlockCount` | `(2)` | `(2)` |
| SignerV2 | `The image is not support SignerV2` | `Using SignerV2` + `Signature verification failed` |
| effective outcome | `AUTHENTICATE fail but allow Kernel binary` | `AUTHENTICATE fail but allow Recovery binary` |
| **`skip_initramfs` in cmdline** | *unknown* | **ABSENT** (2511 chars read in full) |

Both boots are unlocked, orange, and *fail* authentication. The recovery cmdline
provably has no `skip_initramfs`. So **orange/unlocked/AVB-fail is not
sufficient to produce the token.**

**(b) `root=/system` is not an AVB-failure fallback — it is unconditional.**

* Appended in the **boot** path: `last_kmsg:13667`
  `root=PARTUUID=97d7b011-54da-4835-b3c4-917ad6e73d74` (orange, unlocked)
* Appended in the **recovery** path: `last_kmsg:20217` — *identical value*
* Appended on the **other** bootloader, under `green` + valid `SignerV2`:
  `UefiLog1.txt` ledger, `root=/dev/sda24`

Green, orange, boot, recovery, two different bootloaders — `root=` appears in
every case. It is the normal contract, not a fallback.

**(c) ABL's only cmdline-construction logging contains no `skip_initramfs`.**
The 133-byte AVB ledger is complete and arithmetically exact for both the boot
and recovery targets. Neither contains it.

### For — weak

* Our `boot` and `vbmeta` genuinely fail AVB where stock and `dtbo` succeed.
* The normal-boot cmdline is unreadable, so it cannot be *directly* excluded.

### Verdict

**Hypothesis B is not supported.** The only thing that differs between the
recovery boot and the normal boot — in the *logged* evidence — is the target
partition (`Requested Partition: boot` vs `recovery`). Whatever produces
`skip_initramfs` is keyed to the **normal-boot path**, not to AVB state.

## 3. Exact structural differences, stock BOOT vs our BOOT

Both are Android boot header **v0**, `magic = ANDROID!` (0x52444e41).

| field | offset | STOCK | OURS | note |
|---|---:|---:|---:|---|
| `magic` | 0x00 | `0x52444e41` | `0x52444e41` | same |
| `kernel_size` | 0x04 | 50,616,093 | 48,519,996 | different kernel |
| `kernel_addr` | 0x08 | `0x00008000` | `0x00008000` | same |
| **`ramdisk_size`** | 0x0c | **0** | **4,106,247** | |
| **`ramdisk_addr`** | 0x10 | **0** | **`0x02000000`** | |
| `second_size` | 0x14 | 0 | 0 | same |
| **`second_addr`** | 0x18 | **0** | **`0x00F00000`** | we set `BOARD_KERNEL_SECOND_OFFSET` |
| `tags_addr` | 0x1c | `0x01E00000` | `0x01E00000` | same |
| `page_size` | 0x20 | 4096 | 4096 | same |
| `header_version` | 0x24 | 1 | 1 | same |
| **`os_version`** | 0x28 | **`0x18000178`** | **0** | **stock declares Android 12.0 rev 1, vendor patch 24** |
| `name` | 0x2c | `FRPSC27A006` | `FRPSC27A006` | **IDENTICAL — board-name hypothesis dead for good** |
| `cmdline` | 0x3c | 316 chars | 402 chars | ours = stock + exactly the 3 `ramoops.*` params |
| `id` (SHA-1) | 0x43c | `695280f1…` | `e3b14dc0…` | expected |

Neither cmdline contains `skip_initramfs`, `root=`, or `dm-verity`.

### AVB / signature structures (beyond the obvious)

| artefact | STOCK | OURS |
|---|---|---|
| Samsung `SignerVer02` marker | **at 0x3047010** | absent |
| `AVB0` vbmeta magic | **at 0x3048000** | absent |
| `AVBf` AVB footer | **at 0x3FFFFC0** (end of 64 MiB file) | absent |
| boot-image payload ends at | `0x3047000` (50,622,464) | `0x3232000` = **EOF** |
| reserved tail for signature blocks | ~63 MB | **none — mkbootimg left no room** |

So stock is a Samsung-Signed + AVB-descriptor image; ours is a bare mkbootimg
image with no room for any footer. ABL's per-partition verdict for our boot:

```
boot    : GetFooterInfo: Found Footer Info for boot
          Not Using Signer / The image is not support SignerV2
          (Booting) AUTHENTICATE fail but allow Kernel binary: boot     status 1
vbmeta  : Not Using Signer
          (Booting) AUTHENTICATE fail but allow Vbmeta binary: vbmeta
dtbo    : Using SignerV2 / GetFooterInfo: Found Footer Info for dtbo
          Signature verification succeed
          (Booting) AUTHENTICATE Succeed Dtbo binary: dtbo             status 2
```

`dtbo` succeeds precisely because it is a stock partition we never touched.
**This is expected and unavoidable** for any hand-built boot.img without
Samsung's keys — we hold no key that can produce a valid `SignerV2` block.

## 4. Could `ramdisk_size = 0` alone explain it?

**No — not as a rule ABL would apply to our image.**

If ABL's logic were `if (boot_header.ramdisk_size == 0) add skip_initramfs`,
then our image — which carries a 4,106,247-byte ramdisk at `0x02000000`,
byte-identical on-device, and which the kernel demonstrably received and freed —
**would not trigger it.** It triggered anyway.

`ramdisk_size = 0` is a *correlation with stock*, not a demonstrated cause.
Either:

* **(A)** ABL decides without consulting `ramdisk_size` at all — unconditional
  for the normal-boot path. Consistent with everything observed, and with the
  recovery-boot counter-example in §2(a).
* **(C)** ABL consults something else our image gets wrong. The only header
  field with plausible semantics that we get wrong is **`os_version = 0`**
  (stock declares Android 12.0). The other candidates (`second_addr`,
  `header_version`) have no plausible link to initramfs policy.

---

## 5. Could AVB failure explain **both** `skip_initramfs` and forced `root=/system`?

**For `root=`: no — disproven.** It is present for green+SignerV2, for
orange+fail, for boot, for recovery, and across two bootloader builds. It is
the Android system-as-root contract, not a fallback.

**For `skip_initramfs`: not supported, and positively argued against** by the
recovery boot, which shares the identical AVB state and whose fully-readable
cmdline lacks the token.

**What the critical hypothesis actually reduces to.** The idea that ABL
"intentionally forces `skip_initramfs` + `root=/system` to boot the existing
Android despite an unauthenticated custom boot image" is a *coherent* theory
and cannot be fully excluded, because we cannot read the normal-boot cmdline.
But it predicts the token should also appear in the recovery boot's fallback,
and it does not. So the theory has to be narrowed to "…to boot the existing
Android for the **normal** target despite an unauthenticated custom boot
image", at which point it is indistinguishable from **(A)** on the evidence we
have.

## 6. Smallest diagnostic experiment — designed, not executed

**Observable:** a single bit — did our Halium initramfs execute? (presence of
`initrd:` markers / absence of `VFS: Mounted root` in `/proc/last_kmsg`)

**Read-back after each test:** the ABL block in `/proc/last_kmsg`
(`Requested Partition`, the `AVB CMD LINE [...]` ledger, the per-partition auth
verdicts). This tells us *which path ABL took*, but **not** the command line.

### E1 — recommended first (4 bytes, one variable)

Set `os_version` (offset `0x28`) in our BOOT header from `0` to stock's
`0x18000178`. Nothing else changes: same kernel, same ramdisk, same cmdline,
same page size, no signing change.

*Tests:* hypothesis C (OS-version gating). *Prior:* highest available — it is
the only field where our image is semantically wrong rather than merely
different, and ABL is an OS-version-aware bootloader (it stamps
`androidboot.revision`, `wb.*`, and reads fuse-based security state).
*Reversible:* yes, BOOT-only, image is 4 bytes different.
*Risk:* BOOT will not boot our ramdisk if the hypothesis is wrong — same
failure as today. No new failure mode.

### E2 — cheap second (4 bytes, one variable)

Set `second_addr` (offset `0x18`) to `0` to match stock. *Prior:* very low, but
it is a header-shape difference and costs one rebuild.

### Deliberately not proposed

`ramdisk_size = 0` (uninformative — our initramfs could not run either way, and
the ABL log cannot show the cmdline); anything touching dtbo, vbmeta, EFS,
PIT, userdata, `/system`, or encryption; any kernel change (forbidden at this
step).

### Hard limitation to state up front

**No non-kernel experiment available on this device can read the effective
command line.** ABL will not refresh the logfs FAT volume
(`BDS: LogFs sync skipped, Unsupported`, verified: three 8 MiB reads across a
reboot are byte-identical); our bootloader prints no `SEC CMDLINE` at all; and
the kernel has **zero** occurrences of `Command line` in `vmlinux` plus
`console=null`. So header experiments can only ever yield "the ramdisk ran /
did not run" — they can never *explain*.

Each experiment also costs one Odin/Download-Mode session, which has been the
scarce resource in this project.

## 7. The kernel-side workaround

### Exact change

`ShinyKernel/Kernel/init/initramfs.c:613-620` — make the `skip_initramfs`
option parse as a recognised no-op:

```c
static int __init skip_initramfs_param(char *str)
{
-	if (*str)
-		return 0;
-	do_skip_initramfs = 1;
+	/* deliberately ignored for SM-N9750 Halium port:
+	 * ABL injects this via /chosen/bootargs and it suppresses
+	 * unpacking of the boot-image ramdisk. See
+	 * artifacts/device/ITERATION-2-ROOTCAUSE.md */
 	return 1;
}
```

One function body, no config change, no `do_skip_initramfs` flag removal (so the
option stays a recognised parameter and does not become an
`Unknown kernel command line`).

### Is it sufficient by itself? — Yes, provably

With `do_skip_initramfs == 0`, `populate_rootfs()` takes the normal path
(binary-confirmed, `populate_rootfs` at `0xffffff800a4033a0`): it calls
`unpack_to_rootfs` **twice** — `+0xa8` for the built-in archive, then `+0xb8`
for the external initrd — so `/init` is created from our Halium ramdisk.

Overwrite semantics are correct: `init/initramfs.c:341-344` opens targets
`O_WRONLY|O_CREAT|O_TRUNC`, so our ramdisk's `/dev/console` properly replaces
the built-in stub's (5,1) node instead of the unpack silently keeping the stub.

### Would `root=PARTUUID=<system>` still matter? — No, it becomes inert

`prepare_namespace()` has exactly one caller:

```c
init/main.c:1463
	if (sys_access((const char __user *) ramdisk_execute_command, 0) != 0) {
		ramdisk_execute_command = NULL;
		prepare_namespace();
	}
```

With `/init` present and executable, that branch is not taken. `root=` is never
consumed, `mount_block_root()` never runs, and the kernel boots from the
initramfs. **ABL's forced `root=/system` is exactly the thing this change
defeats, and it stops mattering the moment `/init` exists.**

### What the kernel does next

`prepare_namespace()` skipped → `launch_early_services()` →
`ramdisk_execute_command = "/init"` (`init/main.c:1460-1461`) →
`run_init_process("/init")` → our Halium `init` executes.

The initrd is freed after unpacking (as it already is today), so the initramfs
rootfs holds only the ~9 MB of unpacked files. Our `init` must therefore
`mount()` `/data/rootfs.img` (2 GB, block device) from inside the initramfs and
`switch_root` — which is what `scripts/halium` does. If that fails, the
`d2q-rndis.sh` panic path becomes the fallback (note: it creates
`functions/rndis_bam.rndis`, and this kernel does not build `rndis_bam` — a
known, unaddressed gap).

### Interactions and behaviour changes to be aware of

* **Failure mode changes.** Today a bad `/init` silently falls through to
  stock Android. After the change, `run_init_process()` failure **panics**
  ("No working init found") rather than falling back. Better for diagnosis,
  but the device will sit on a panic screen instead of bootlooping to recovery.
* `rootwait` / `rootflags` handling and `mount_block_root()` are skipped — both
  irrelevant here.
* `load_default_modules()` still runs (`init/initramfs.c:681`); our ramdisk
  ships no modules, so it is a no-op.
* It deviates from the vendor kernel's intent. If ABL's `root=` were ever
  genuinely required, the device would hard-panic instead of booting Android.
* Must be rebuilt with the ShinyKernel toolchain per `Kernel/build.txt`
  (`-j2`, not `-j8`) and re-verified with `tools/check-reproducible.sh`.

## 8. Recommendation

**Do the kernel-side change next, not another speculative header flash.**

Reasoning:

1. It is **one build and one Odin session**, versus one session per header
   experiment — and the header experiments have a low prior and cannot
   *explain*, only confirm by luck.
2. It is **provably sufficient** given the source + disassembly analysis, and it
   makes ABL's `root=/system` inert rather than fighting it.
3. It is simultaneously a **diagnostic**: if the Halium initramfs then runs,
   the entire `skip_initramfs` theory is confirmed end-to-end at runtime for
   the first time. If it does *not* run, the theory is wrong and we have learned
   that cheaply — which is strictly more information than any header flip.

**Strongly recommended addition to the same build, at no extra device cost:**
add a one-line early print of the command line, so the unobservable becomes
observable:

```c
/* arch/arm64/kernel/setup.c, in setup_arch(), before parse_early_param() */
pr_info("BootLoader command line: [%s]\n", boot_command_line);
```

`KERN_INFO` goes to the ring buffer regardless of `console=null`, and
`/proc/last_kmsg` under TWRP has been capturing `KERN_INFO` reliably all
along (we have ~650 of them). This would finally let us read the complete
ABL-generated `/chosen/bootargs` — including `skip_initramfs` in place — and
close the last open question from iteration 3.

One build, one flash, both the fix and the missing observability.

**Not recommended before that:** E1/E2 header experiments, and any further
attempts to read ABL's command line from logs — that channel is exhausted
(`BDS: LogFs sync skipped`; no `SEC CMDLINE`; no kernel printk).

## Evidence classification

**Directly observed (device/local files this iteration):**
header fields of both images; `SignerVer02`/`AVB0`/`AVBf` present in stock and
absent in ours; `os_version` 0x18000178 vs 0; `name` identical; cmdline
byte-prefix identity; 2511-char recovery cmdline with no `skip_initramfs`;
per-partition ABL auth verdicts; ABL ledger for boot and recovery; `abl` (sdd6)
is a cert/signature blob (`Samsung Root CA cert`, `SignerVer02`, `avbtool 1.1.0`).

**Source-confirmed:** `init/initramfs.c:622-690`; `init/main.c:1460-1466`;
`drivers/of/fdt.c:1190-1240`; `mm/page_alloc.c:6971`; `arch/arm64/mm/init.c:811`;
`init/initramfs.c:341-344` (`O_TRUNC` overwrite).

**Binary-confirmed:** `populate_rootfs` disassembly — `do_skip_initramfs` tested
first, single `printk` at `+0xa4` unreachable when set, string at
`0xffffff8009f92d58`; double `unpack_to_rootfs`; absence of any
`Command line` string in `vmlinux`.

**Inferred (flagged as such):** that ABL keys `skip_initramfs` to the
normal-boot path rather than to AVB state — supported by §2(a) and §5, not
directly read; `DstLen` semantics = remaining buffer space (arithmetically
self-consistent across three boots, absolute capacity not pinned); that ABL
generated the ~2.4 KB seed (from the 4296 start and the 2511-char recovery
cmdline).

**Not established:** the literal text and position of `skip_initramfs` in the
normal-boot `/chosen/bootargs`; whether ABL reads `os_version`; ABL's internal
code path (its code is encrypted at rest — the `abl` partition contains only
certificates and `avbtool` metadata, not readable code).
