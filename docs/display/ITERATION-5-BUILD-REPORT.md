## 1. Exact source changes

Both files were mode `444` in the read-only kernel tree. Pristine state was

### 1a. `ShinyKernel/Kernel/init/initramfs.c` — 20 changed lines

```diff
@@ -612,9 +612,23 @@
 static int __init skip_initramfs_param(char *str)
 {
-	if (*str)
-		return 0;
-	do_skip_initramfs = 1;
+	/*
+	 * SM-N9750 Halium port.  See
+	 * artifacts/device/ITERATION-2-ROOTCAUSE.md
+	 *
+	 * Samsung ABL supplies the whole command line through
+	 * /chosen/bootargs, and on the normal-boot path it includes
+	 * "skip_initramfs".  That makes populate_rootfs() free the boot
+	 * image ramdisk without unpacking it; /init then does not exist,
+	 * prepare_namespace() runs, and the kernel mounts ABL's root= --
+	 * the stock Android /system partition.
+	 *
+	 * Recognise the parameter so it is not reported as unknown, but do
+	 * not set do_skip_initramfs, so the Halium initramfs is unpacked
+	 * normally.  prepare_namespace() is then never reached and root=
+	 * becomes inert.
+	 */
+	(void)str;
 	return 1;
 }
 __setup("skip_initramfs", skip_initramfs_param);
```

`__setup()` registration, parameter name and handler name are untouched. The
`if (do_skip_initramfs)` branch inside `populate_rootfs()` is deliberately left
in place — it is simply no longer reachable from the command line.

**Binary proof of the intended behaviour.** `skip_initramfs_param` is now 12 bytes,
two instructions, no store to `do_skip_initramfs`:
```asm
ffffff800a40337c:  mov  w0, #0x1   // =1
ffffff800a403380:  ret
```
`do_skip_initramfs` is **absent from the symbol table** — the compiler proved it
dead and eliminated the entire skip branch. `populate_rootfs` now begins directly
with the built-in unpack, the printk, then the external unpack:
```asm
ldr  x1, [x26, #0x518]        ; __initramfs_size
add  x0, x0, #0x318           ; __initramfs_start
bl   unpack_to_rootfs         ; built-in stub FIRST
cbnz x0, …                    ; panic on error
ldr  x8, [x24, #0x88]         ; initrd_start
cbz  x8, …
bl   printk                   ; "Trying to unpack rootfs image as initramfs..."
bl   unpack_to_rootfs         ; external initrd SECOND
```

Symbol count fell 149,163 → 149,162, exactly the one removed variable.

## 9. Difference attribution — and an honest negative result

A control rebuild was run with the **pristine** source and the same defconfig into
a separate output tree (`artifacts/control-rebuild/out-control`).

**Result: the kernel build is NOT byte-reproducible in this environment.**

```
baseline (7dedfea6)      vs control-pristine (108491bf) : 3,651,356 bytes in 447,260 runs
baseline (7dedfea6)      vs iter5-fixed   (123a29cf)    : 5,245,384 bytes in 550,831 runs
control-pristine          vs iter5-fixed                 : 4,958,021 bytes in 551,549 runs
```

All three have **identical size** (48,519,996 B), identical config hash, and
identical DTB offsets and content. The control build was built from unmodified
source, so the 3.65 MB is entirely build-to-build variation, not my change.

Diagnosis: 98.2 % of the 149,163 symbols sit at **identical addresses** between
baseline and control, so this is not layout drift — it is build-dependent
*content* at stable addresses, spread across the image with a concentration in
the 0x1c00000-0x2400000 region. Embedded build metadata does differ (the version
string carries the build time and a build counter that incremented to `#2` in
iter5: `#1 … 17:54:21` baseline, `#1 … 22:08:42` control, `#2 … 21:32:16` iter5),
but the string lengths are identical, so metadata alone does not explain 3.65 MB.
The exact source was not chased further; the project has no kernel-side
reproducibility harness (`tools/check-reproducible.sh` covers the **rootfs**
only, and was therefore not applicable here).

**Consequence, stated plainly:** the 5,245,384-byte iteration-2 → iteration-5
kernel-payload delta **cannot** be attributed, even approximately, to the two
source changes. I am not claiming that. The reliable evidence for the change is
the semantic and binary evidence in section 8, which is direct and
configuration-independent:

* `skip_initramfs_param` compiles to `mov w0,#1; ret` — verified by disassembly
* `do_skip_initramfs` eliminated from the symbol table as dead
* `populate_rootfs`'s skip branch removed; two `unpack_to_rootfs` calls now unconditional
* diagnostic string present; `Trying to unpack rootfs image as initramfs...` retained
* config byte-identical, DTBs byte-identical, ramdisk byte-identical, boot header
  identical except the SHA-1

A useful side observation: baseline→iter5 moves only 4.4 % of symbols (vs 1.8 %
for the pristine control), and `populate_rootfs` moved down by exactly `0x18` bytes
— consistent with the 24 bytes of skip-branch code the compiler removed.

## 10. Expected runtime behaviour (for later, if this image is flashed)

```
ABL /chosen/bootargs
        |
        +-- skip_initramfs
        |
        v
kernel parses the parameter (recognised) but leaves do_skip_initramfs == 0
        |
        v
populate_rootfs()
        |
        +-- unpack built-in 512-byte initramfs   (stub: dev/, dev/console, root/)
        |
        +-- printk "Trying to unpack rootfs image as initramfs..."
        |
        +-- unpack external Halium initramfs     (our /init, overwriting the stub's /dev/console)
        |
        +-- free_initrd()  ->  "Freeing initrd memory: 4008K"  (as before)
        |
        v
/init exists and is executable
        |
        v
init/main.c:1463  sys_access("/init") == 0  ->  prepare_namespace() NOT called
        |                                     ABL's root=PARTUUID=97d7b011-… is never consumed
        v
run_init_process("/init")  ->  Halium /init executes
```

And, from `setup_arch()` at t≈0, before anything above:
```
BootLoader command line: [<complete ABL /chosen/bootargs>]
```
which should finally expose the previously invisible `skip_initramfs` token in
`/proc/last_kmsg` under TWRP.

**Behaviour change to be aware of:** if the Halium `/init` fails, the kernel will
now **panic** ("No working init found") instead of silently falling through to
stock Android. That is better for diagnosis, but it means a panic screen rather
than a bootloop to recovery.

**Known follow-on gap (unchanged by this build):** the `d2q-rndis.sh` panic path
creates `functions/rndis_bam.rndis`, and this kernel does not build `rndis_bam`
(no such symbol in `vmlinux`). If `/init` panics before the rootfs switch, the
intended RNDIS rescue path may not come up.
