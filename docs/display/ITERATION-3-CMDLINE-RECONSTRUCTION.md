# Iteration 3 — Reconstructing ABL's `/chosen/bootargs`

One clean boot performed (device came offline 18:09:04Z, back online 18:09:49Z).
Everything else read-only: `adb shell dd if=`, `mdir`/`mcopy`, `readelf`, `llvm-objdump`.
No flash, no reboot by me beyond the authorised one, no partition writes.

---

## TL;DR

The reconstruction **partly succeeded and partly failed, for a reason that is now
known**. ABL's append ledger for our boot is fully recoverable. The ~2.4 KB seed
that ABL generates before that ledger is **not logged at all** by our bootloader,
and the kernel has no code that prints its command line, so the one token that
matters (`skip_initramfs`) cannot be read off this device by any available
channel. Its *presence* is proven three ways; its *textual location* is not.

**Correction to `ITERATION-2-ROOTCAUSE.md`:** the `root=` value I previously
reported (`root=/dev/sda24`) came from a stale log written by a **different
bootloader**. Our bootloader appends `root=PARTUUID=97d7b011-…`. The conclusion
(root filesystem = stock Android `/system`) is unchanged and independently
confirmed at runtime.

## 1. The reconstructed ABL `/chosen/bootargs`

### 1a. What is exactly recoverable: ABL's AVB/dm-verity append layer

From `iter2-last_kmsg:13650-13667` — the normal-boot ABL block
(`:13643 Requested Partition: boot`), which ends at `:13853 Exit EBS` and is
immediately followed by our kernel at `:13854`:

| # | SrcLen | appended string | DstLen after |
|---|-------:|-----------------|-------------:|
| — | — | *(seed, unlogged)* | 4296 |
| 1 | 31 | ` androidboot.verifiedbootstate=` | 4265 |
| 2 | 6 | `orange` | 4259 |
| 3 | 24 | ` androidboot.keymaster=1` | 4235 |
| 4 | 1 | ` ` | 4234 |
| 5 | 19 | ` androidboot.ulcnt=` | 4215 |
| 6 | 2 | `2 ` | 4213 |
| 7 | 50 | `root=PARTUUID=97d7b011-54da-4835-b3c4-917ad6e73d74` | 4163 |

Total appended: **133 bytes**. The `DstLen` ledger is arithmetically exact and
self-consistent across three separate boots (4296 start; decrements equal
`SrcLen` every time), so the ledger is complete for this pass.

`last_kmsg:13665` `dm-verity cmdline Append!!` sits between appends 6 and 7,
i.e. append 7 is the dm-verity `root=` injection.

**`skip_initramfs` is not in this ledger.**

### 1b. What is not recoverable, and why

ABL's seed is **not our `BOARD_KERNEL_CMDLINE`**. Evidence:

* Our header cmdline is **402 chars**. ABL's own ledger starts at `DstLen 4296`,
  i.e. ~2.4 KB were already in the buffer before the AVB pass.
* The only ABL-generated cmdline we can read in full is the **recovery** one,
  **2511 chars**, dominated by `androidboot.*` properties ABL itself synthesises
  (`serialno`, `dtbo_idx`, `sec_atd.tty`, `sec_log=0x200000@0xC1600000`,
  `wb.*`, `em.*`, `carrierid`, …). None of that is in our header cmdline.
* On the *other* bootloader, ABL's ` Orig :` echo of the incoming cmdline was
  **233 chars and had `androidboot.console=ttyMSM0` removed** relative to our
  402-char header — so ABL demonstrably rewrites, filters and extends the seed.

Therefore the effective command line is a **~2.5 KB string wholly generated by
ABL**, and our `BOARD_KERNEL_CMDLINE` is only one input to it.

### 1c. Why our bootloader does not log it

`drivers/of/fdt.c:1190-1240` (this tree, `CONFIG_CMDLINE=""`, no
`CONFIG_CMDLINE_FORCE`, no `CONFIG_CMDLINE_EXTEND`):

```c
#else /* CMDLINE_FROM_BOOTLOADER */
static const int overwrite_incoming_cmdline;   /* 0 */
static const int read_dt_cmdline = 1;           /* 1 */
static const int concat_cmdline;                /* 0 */
#endif
...
	if (read_dt_cmdline)
		p = of_get_flat_dt_prop(node, "bootargs", &l);
	if (p != NULL && l > 0) {
		if (concat_cmdline) { /* append */ }
		else strlcpy(cmdline, p, min((int)l, COMMAND_LINE_SIZE));   /* REPLACE */
	}
```

`/chosen/bootargs` **replaces** `boot_command_line` wholesale. ABL writes that
node itself (`last_kmsg:13832 Update Device Tree total time: 140 ms`,
`:13830 ERROR: Could not get splash memory region node`,
`:1114/13814`-area `kaslr-Seed is added to chosen node`).

Our boot's ABL block contains **no** `sec_update_cmdline` and **no**
`SEC CMDLINE` record — verified by grepping lines 13400-13853. The only
bootloader that emitted it truncated it at a hard 512-byte line cap anyway
(measured: record = 510 bytes + CRLF = 512).

## 2. Exact location/source of `skip_initramfs` — NOT OBSERVED

Stated plainly, because the evidence is one-sided:

**Observed / proven:**

* `do_skip_initramfs == 1` during our boot. Three independent ways:
  1. **Source** — `init/initramfs.c:622-630`; line 628 `free_initrd()` is the
     only caller of `free_initrd()` that does not first `printk`.
  2. **Binary** — disassembly of `populate_rootfs` (`0xffffff800a4033a0`):
     `do_skip_initramfs` is tested first (`cmp w8,#0x1` / `b.ne`); if set it calls
     `free_initrd_mem` at `+0x80` and jumps to `default_rootfs`. The
     `bl printk` at `+0xa4` is a single basic block reachable **only** from the
     non-skip path. Its string is at `0xffffff8009f92d58`:
     `"\x016Trying to unpack rootfs image as initramfs...\n"`, immediately
     followed by `"rootfs image is not initramfs..."`.
  3. **Runtime log** — `Freeing initrd memory: 4008K` present;
     `Trying to unpack rootfs image as initramfs` absent (0 hits, though the
     string is in the binary); log continuous across that instant.
* Also proven by the size arithmetic: 4,106,247 B → 1002 whole pages →
  4,104,192 B → `1002 << (12-10)` = **4008K**. That is *our* ramdisk.
* Independently corroborated by the stub: `Warning: unable to open an initial
  console.` — `/dev/console` **is** in the 512-byte built-in initramfs, so the
  built-in archive was not unpacked either, which only the skip path allows.
* Its only setter in the entire tree is
  `init/initramfs.c:611-620`, `__setup("skip_initramfs", skip_initramfs_param)`,
  a **command-line** parameter. It arrived with the initial import of Samsung's
  4.14.190 tree (`f8ade4ccc`, "Initial import of Android common kernel
  4.14.190 (d2q_chn_hk bootable sources)") — vendor code, not ours.

**Ruled out as the source:**

* Our BOOT header cmdline — 402 chars, inspected directly from the packed image:
  no `skip_initramfs`.
* ABL's AVB append ledger for our boot — 133 bytes, itemised above.
* The 2511-char recovery cmdline — no `skip_initramfs` (expected: recovery uses
  its ramdisk, `androidboot.boot_recovery=1`).
* The `dtbo` partition — all 15 DTBO entries extracted and parsed; **every one is
  a valid FDT with no `/chosen` node and no `bootargs` at all**. Whole-partition
  literals `chosen` 0, `bootargs` 0, `skip_initramfs` 0.

**Conclusion:** `skip_initramfs` must be inside the unlogged ~2.4 KB of ABL's
generated seed, in the part of `/chosen/bootargs` that our bootloader never
prints and that the other bootloader truncated at 512 bytes. **I have not read
the literal token off the device, and I do not claim to have.**

### Why no channel can close it

* **ABL does not refresh the logfs FAT volume.** `iter2-last_kmsg:13849` and
  `:20384`: `BDS: LogFs sync skipped, Unsupported`. Confirmed empirically: three
  full 8 MiB reads of `logfs` spanning the clean boot are **byte-identical**
  (`sha256 1235cbb0…`, 0 differing bytes).
* **The kernel cannot print its command line.** `arch/arm64/kernel/setup.c:355`
  only does `*cmdline_p = boot_command_line;` — there is no printk. Binary
  search: `vmlinux` contains **0** occurrences of `Command line`,
  `Command line: `, or `Kernel command line`. Plus `console=null`. So
  `/proc/cmdline` of a *running* our-kernel is the only runtime source, and our
  kernel never survives to userspace.
* The runtime DTB lives only in RAM during boot; the on-flash `dtbo` has no
  `/chosen`.

## 3. Exact source of `root=` — SOLVED

Samsung ABL, in its AVB/dm-verity command-line pass:

```
last_kmsg:13665   dm-verity cmdline Append!!
last_kmsg:13666   DstLen 4213, SrcLen 50
last_kmsg:13667   AVB CMD LINE [root=PARTUUID=97d7b011-54da-4835-b3c4-917ad6e73d74]
```

Not from our image, not from the DTB, not from the kernel. ABL hard-wires it.

Runtime confirmation that this PARTUUID is stock Android `/system`:

```
last_kmsg:16966   EXT4-fs (sda24): mounted filesystem without journal. Opts: (null)
last_kmsg:16967   VFS: Mounted root (ext4 filesystem) readonly on device 259:8
/proc/partitions  259   8   6492160 sda24
/dev/block/bootdevice/by-name/system -> /dev/block/sda24      (6.2 GB)
```

### Why the earlier report said `root=/dev/sda24`, and why that was wrong

`UefiLog1.txt` in logfs is from a **different bootloader and a different boot**:

| evidence | our boot (`iter2-last_kmsg`) | `UefiLog1.txt` |
|---|---|---|
| bootloader string | `N9750ZSU6HZE1` | `N9750ZSU6HXE1` |
| `USRF GetUserPartitionFlashed` | `0x55535246` | `0x454E4F44` |
| `[SWWP] Value` | `0x31F,0x0,0x0` | `0x0,0x1,0x0` |
| `verifiedbootstate` | `orange` | `green` |
| `ulcnt` | `2` | `0` |
| `root=` | `PARTUUID=97d7b011-…` | `/dev/sda24` |
| `Requested Partition` | `boot` | (not shown) |

`HZE1` vs `HXE1` is a different bootloader build. Nothing in that file
describes our boot. My previous report used it for the `root=` value — that was
wrong; the ledger in `last_kmsg` is the right source. The overall diagnosis is
unaffected because the runtime log independently pins the root filesystem.

## 5. Uncertainty from missing / corrupted records

1. **The logfs FAT12 channel is dead for ABL.** `BDS: LogFs sync skipped,
   Unsupported`; three 8 MiB reads across a reboot are byte-identical.
   `UefiLog1.txt` is a factory-era artifact from bootloader `HXE1`.
2. **`SEC CMDLINE` is capped at 512 bytes** (measured 510 + CRLF), so even
   `HXE1` never logged a complete command line. The ` Orig :` line is also
   damaged by a second message overwriting its tail
   (`…vendor/firmw` + `accic_check_active`).
3. **Our bootloader logs the AVB ledger but no `SEC CMDLINE` at all**, so the
   ~2.4 KB seed is unrecoverable from any log.
4. **Runtime capture is impossible** — the kernel contains no command-line
   printk (0 occurrences of `Command line` in `vmlinux`) and `console=null`.
5. **`DstLen` semantics are inferred** (remaining buffer space). The arithmetic
   is exact and reproduces across three boots, but the absolute buffer capacity
   is not pinned, so "4296 free" cannot be converted into a seed length.
6. **Provenance risk in `/proc/last_kmsg` itself.** The file interleaves several
   boots (kernel sessions plus ABL blocks for `boot` and `recovery` targets).
   I attributed the ABL block to our boot on three grounds: `Requested
   Partition: boot`, adjacency to our kernel log with no intervening session,
   and `boot`/`dtbo` authentication records. This attribution is an inference,
   not a logged boot id.
7. The clean boot added **no new evidence** — it confirmed the logfs channel is
   dead and produced a TWRP `/proc/last_kmsg` that has now overwritten the
   iter-2 capture. The iter-2 copies under `artifacts/device/logs/` are the only
   surviving record of that boot; **they should be treated as irreplaceable.**

## What this means for the port

The blocker is now precisely characterised: **Samsung ABL supplies the entire
command line, and its `root=` is hard-wired to stock `/system`.** The only
thing standing between us and our Halium initramfs is one token in a string we
cannot read.

Realistic levers, none of them authorised, none of them tried:

1. **Find out whether ABL emits `skip_initramfs` conditionally** — e.g. it may
   key off the boot image having `ramdisk_size == 0` (the stock boot.img), or
   off a signature/AVB result. Our image has a 4 MB ramdisk and ABL still
   discarded it, but a differently-*signed* or differently-shaped image might
   take another path. The ABL log shows our boot partition fails AVB
   (`(Booting) AUTHENTICATE fail but allow Kernel binary: boot`, `Not Using
   Signer`, `boot state: orange`) — the stock path is `green` with a valid
   `SignerV2`. That asymmetry is the most promising unexplored variable.
2. **Kernel change** — ignore or drop the `skip_initramfs` `__setup`. Direct,
   small, and provably sufficient given the binary analysis. Requires
   authorisation and a rebuild.
3. **Put a root filesystem where ABL points** — i.e. replace `/system`. Destructive;
   not recommended and not authorised.
